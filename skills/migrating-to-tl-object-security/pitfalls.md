# Pitfalls and common mistakes

Check this list whenever something works as root but not for a test user, or before a review of
the configuration. Each row: the mistake or symptom, and what to do instead.

## Pitfall: side effects that throw roll back the whole command

Mail sending is the usual case. `sendMail` throws when SMTP is not active (local dev) or the server
fails, and the exception rolls back the whole transaction, including deletes done before it. Only the
UI shows a message, the log stays empty. In migrated or privileged functions, wrap notifications in
`try(sendMail(...), catch: e -> { info(...); false })`. Don't mistake the resulting "delete
doesn't work" for a security denial.

## Common mistakes and symptoms

| Mistake | Fix |
|---|---|
| Mirroring profiles into module grants ("role has Write in this view → Write on the module") | Grant only the roles that reach the type. Coverage flags the rest as dead grants. |
| Object grants for root-only roles (SYSADMIN, USER) | Dead unless the type delegates to the root. Decide explicitly. |
| `without-security` on role carriers to "make the UI work" | Opens them to every user and the API. Grant or delegate instead. |
| Read everywhere for select fields | Discover suffices for options showing labels. |
| Testing as root | Use one non-admin test account per role. Accounts with `Person.admin=true` bypass checks just like root, so check the flag on existing "admin" demo accounts. |
| Putting test accounts into `WEB-INF/data/*.objects.xml` | That data is imported in production. Put them into the **local deploy aspect** (`deploy/local/webapp/WEB-INF/data/`) and wire assignments with an idempotent startup `ScriptTask` in `deploy/local/webapp/WEB-INF/autoconf/` (details: `engine-reference.md` §Test-user setup). Scripted tests run per action with `user-id="<account>"`, with no password needed. |
| Test fixture resolves master data by name across tenants (`all(T).filter(name)`) | Names repeat across tenants; resolve within the tenant. Verify the fixture on a fresh DB and log the resulting roles with `filterPermission(…, "<account>")`. |
| Mandatory references to accounts (e.g. an owner/creator copy for role rules) | Never make references to `tl.accounts:Person` mandatory: accounts get deleted (e.g. cleanup of invited users). Rely on a default value (`currentUser()`) instead of setting it explicitly, and verify in a test that the default applies (script `new`, privileged functions, copies). |
| Scripts that **detach a composition part and then delete it** (`$c.set(parts, without x); $x.delete()`) | Under object security the delete of a part is checked against its container; once detached it has no container → "may not delete". Delete first, then update the list. Typical symptom: deleting works in the edit form but fails in a bulk/replace operation. Grep for `.delete()` preceded by a `set`/`remove` on the composition. Same for **moving** a part: between detach and attach every check denies, `get` silently returns empty values (copied attributes become null). Decisions are cached per interaction and KB revision (`AccessDecisionCache`), and an uncommitted transaction makes no new revision, so the outcome depends on whether the part was checked before the detach. Attach to the new container first, or don't touch the part in between, or do the restructuring in a privileged function. |
| Scripts that read **model metadata** reflectively (`$attr.get(tl.model:TLStructuredTypePart#type)` as dynamic grid `columnType`, `TLClass#specializations`, `TLReference#composite` in merge dialogs) | Model elements are persistent BoundObjects; Discover never filters them, but `get` on their attributes checks Read, and nobody configures `tl.model` → deny by default → empty values for non-admins (NPE in `ColumnInfoFactory`, silently wrong filters). Fix once: `<class name="tl.model:TLModelPart"><access-parent><script expr="p -> \`SecurityStructure#ROOT\`"/></access-parent></class>` (Read via the root's USER grant; inherited by all model types). Not `without-security`: that would allow writing the model by script/API. |
| Grid/table with `securityObject="model"` whose rows are composition parts (e.g. tenant master data) | Legacy, not object security: `model` = path element `Model`, index 0 = **the model passed to the command** (the target), not the component model (the in-app label "Aktuelles Modell" misleads). Edit/delete buttons target the selected row → `AccessManager.hasRole(user, row, profile roles)`; rows without legacy roles (no role rule/security parent) → "keine Berechtigung" for non-admins. With `multiSelection="true"` the target is a set → security object `null` → no check at all (looks like it works). Fix: `securityObject="model(self())"` (component model = the tenant) or a channel to the tenant, e.g. `selection(<tenant list>)`. Rule out object security first with a REST probe (`canWrite`). |
| Derived attribute (`<storage-algorithm><query>`) that collects objects from a secured substructure | `AttributeByExpression` always runs **unsecured** (definer's rights, for caching/determinism); only the Read grant on the attribute itself applies. It shows e.g. all areas/measures although the user may read only some, while a computed table column (`ComputedColumnProviderByExpression`, secured) with the same expression shows only the permitted ones. If the result must respect the reader's rights, compute it in a secured script (layout column, function) instead, or restrict the attribute with a part grant. `MacroAttribute` keeps security. |
| App AccessManager config with `config:override="true"` (as the in-app editor writes it) | It drops **all** framework role rules and role parents, e.g. `PersonalProfileForPerson`/`-Contact` (users can't read their own account → personal settings broken for non-admins), contact and invitation role parents. List the framework `*-web-fragment.war` files contributing AccessManager config and re-add what the app needs. Symptom: framework grants reported as dead by coverage. |
| Making an operation privileged because it "sees too little" | First ask whether seeing less is the desired behaviour (tenant scoping). Privilege only data the user must not see but the transaction must process. |
| A system context around whole scripts | Use `<privileged-script>` with a command-group check, or rely on the already unsecured constraints and derived attributes. |
| "Keep legacy authoritative and intersect" | Both layers apply simultaneously and independently. Plan for both. |
| Marking a base type `without-security` to silence coverage for a transient subtype | Marks propagate to **all** subtypes, including persistent ones (e.g. a persisted context type extending a transient base). Mark the transient leaf types individually. Validate every type name against the model before restarting: an unknown type fails the whole service at startup. |
| Role parent on the **type** of a singleton (e.g. default pictures, installer file) | If the app copies the singleton into other objects (e.g. a default picture copied into each new document as a composition part), the role parent also hits the copies: creation is denied, and the copies become readable by everyone. Use an access-parent script instead: `x -> if($x.container() == null, <root singleton>, $x.container())`, and give the root type the grants for the singleton. |
| `inherit="true"` on grants for framework types (e.g. `tl.accounts:Group`) | Also hits framework subtypes (e.g. per-user representative groups) that lack your role parent → dead grants. Omit `inherit` there. |
| Reading a "dead Create grant" finding literally | Top-level creation is checked on the security root (or the passed `context:`); the coverage check ignores that context. Delete/Write are checked on the instance, so dead findings there are real. |
| Expecting a module grant to cover submodules (`app.x` covering `app.x.y`) | A module entry covers only its own classes. `inherit` means subtypes, not submodules. |
| Granting profile-only command groups as object operations | Grant a custom group on a type only where object-level code checks it (`canExecute`, `<privileged-script command-group=>`). It must be a registered command group, or startup fails. |
